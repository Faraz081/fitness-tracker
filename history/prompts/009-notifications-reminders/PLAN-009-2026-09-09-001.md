## Prompt

/sp.plan

Plan the Notifications & Reminders feature for FitTrack (Day 6.1) as a frontend-only, JavaScript feature. Plan in phases and provide a recommended implementation order.

Proposed phases:

1. **Foundation** — Sidebar item (Notifications), the `/notifications` page routed inside the existing DashboardLayout (Pattern A), and the notification data model.
2. **Notification Creation Logic** — Create event notifications at the correct moment (workout completed, goal progress, goal completed) and reminders (workout, meal, goal) with relevance guards and same-day deduplication; respect settings.
3. **Notifications Page** — Chronological list, type chips/icons, timestamps, read/unread visual states, dismiss/clear, mark-all-read, filter tabs, empty states.
4. **Notification Settings** — Per-type enable/disable (6 toggles, default all enabled), mute-all, persisted, respected by every surface (list, badge, toasts).
5. **Integration & Polish** — Toast integration via the existing `useToast`/`ToastContainer`, unread badge in sidebar (99+ cap), liveliness, responsive + a11y pass, regression, build verification.

Recommended implementation order: 1. data model + sidebar entry + page layout, 2. trigger logic, 3. read/unread + badge, 4. settings, 5. reminder logic, 6. polish + verification.

Definition of done: all three user stories demonstrable; all 26 functional requirements implemented; all 10 success criteria met (including persistence across reload, empty pages, and settings suppression); `npm run build` clean; zero backend/env/new-dependency changes; constitution (Day 6.1 N1-N10) re-verified at the end.

Constraints: JavaScript-only (no TypeScript); no new npm dependencies; no backend, API, env, or model changes; single localStorage key `notificationsState` (narrow N9 exception); additive-only route/nav edits; dark theme tokens only.

### Key Decisions

1. **Route pattern**: Pattern A — top-level `<ProtectedRoute><Notifications/></ProtectedRoute>`
   wrapping `DashboardLayout` (satisfies "renders inside existing DashboardLayout").

2. **Nav**: additive `SIDEBAR_MENU` entry + `menuIcons` `Bell` + unread badge (99+
   cap); rendered app-wide because `Sidebar` is used by both `Layout` and
   `DashboardLayout`.

3. **State**: new `NotificationsProvider` in `main.jsx` (inside `AuthProvider`);
   consumed via `useNotifications()`. Provider owns a single `useToast` +
   `ToastContainer` so toasts work on Pattern A pages (removed the duplicate
   container from `Layout.jsx` — justified in Complexity Tracking).

4. **Persistence**: no `useLocalStorage` existed, so plan adds a minimal
   `hooks/useLocalStorage.js` (our own utility — not a dependency) for the
   single key `notificationsState` (N9); S5 filter persistence stays banned.

5. **Derivation model (central mock-phase tension)**: seeds in
   `data/notificationsData.js` (mirroring the mock app state, exactly like
   `analyticsData.js` composes) + pure generators in `utils/notificationsUtils.js`
   with relevance guards and `eventKey = type:entityId:YYYY-MM-DD` dedup. One
   live frontend trigger: `WorkoutForm` create-success calls `onWorkoutLogged`
   (FR24 "correct moment"); goals/meals have no mutable frontend flow so they
   are seed-derived. Swappable for a future API.

6. **Toast behavior**: toasts fire only for live-created notifications (e.g.
   workout completion); on load the reminder set surfaces via page + badge only
   (no toast storm — "Respect Attention").

7. **Project Structure**: constitution-mandated `components/notifications/`
   (4 files), `utils/notificationsUtils.js`, `data/notificationsData.js`;
   contracts produced as a frontend data/storage contract (no HTTP) named
   `notification-contract.md`.
