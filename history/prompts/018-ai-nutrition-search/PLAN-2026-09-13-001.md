## Prompt

Planning task (user input, /sp.plan). Structure phases: Phase 1 Foundation — review Nutrition page & meal logging flow, confirm model & API, integration points, auth scoping. Phase 2 Secure Gemini Lookup — `GEMINI_API_KEY` backend support, backed endpoint/service, natural-language input, real-time Gemini call, structured return including Fiber/Sugar/Sodium, backend validation, graceful errors, key never exposed to frontend. Phase 3 Search UI — single search bar (food name only), live lookup on search, loading state, result card (name + AI badge, per-serving macros, second row Fiber/Sugar/Sodium, "+" action). Phase 4 Add-to-Log Modal — opens on "+", Close X, nutrition breakdown, editable Quantity (g), live recalc "For [X]g: [Y] kcal | P | C | F" strictly from real AI data (no hardcoded ratios), Add To dropdown (Breakfast/Lunch/Dinner/Snacks), Cancel & "+ Add Food". Phase 5 Persistence & Meal Integration — save to real backend/DB with user ID + food name + meal type + quantity + nutrition, real-time under selected meal, no local-only storage, empty meal states. Phase 6 Real-Time Updates & Cleanup — no manual refresh, meal sections + totals reflect saves, remove static/placeholder nutrition, enforce user-scoped data. Phase 7 Verification — search common foods, modal quantity recalc, save to each meal correct placement, persistence after refresh, empty state, Gemini failure/unrecognized food, cross-user isolation. Recommended order 1–7. Definition of Done: food-name-only searches always hit live AI; dynamic result card/modal; live quantity recalc; real DB save; real-time meal placement; correct empty states; no static source of truth; user-scoped logs.
