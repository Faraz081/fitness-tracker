## Prompt

/sp.specify Create a detailed functional specification for the Search &
Filtering system of the FitTrack application based on the constitution already
defined.

### Feature: Search & Filtering (5.1)

1. Overview: Provide fast and consistent search + filtering across Workouts,
   Exercises, and Nutrition records so users can quickly find what they need.

2. Global Search: A global search input should be available (preferably in the
   top area or a consistent location). Typing in the global search should allow
   users to find workouts, exercises, and nutrition records. Results should be
   grouped by type or clearly labeled. Search must be case-insensitive and
   update as the user types (with debouncing).

3. Entity-Specific Search: Workouts searchable by workout name and notes.
   Exercises searchable by exercise name. Nutrition searchable by food/meal
   name.

4. Filters: Date filter (single date or date range; applicable to Workouts and
   Nutrition records), Workout Category Filter (Strength, Cardio, Hypertrophy,
   etc.), Meal Type Filter (Breakfast, Lunch, Dinner, Snack, etc.). All
   filters combinable with search.

5. Clear Filters: A clearly visible "Clear filters" (or "Reset") option must
   appear whenever any filter or search is active. Clicking it must reset
   search text and all filters to default and show the full list again.

6. Behavior Rules: Filters and search can be used together. Results update
   immediately after filter changes. Maintain the current filter/search state
   while the user stays on the page. When no results match, show a clear empty
   state with a message and a way to clear filters.

7. UI Rules (Strict): Search bar and filter controls must match the existing
   FitTrack design system (dark theme, green accents, same input/card styles).
   Layout and spacing must stay consistent with the Dashboard (tight content,
   minimal side gaps). Active filters should be visually indicated. Empty
   states must be helpful and consistent with the rest of the app.

8. Acceptance Criteria: Global search works across workouts, exercises, and
   nutrition; entity-specific search works correctly; date filter works;
   workout category filter works; meal type filter works; multiple filters can
   be combined; clear filters resets everything; empty states are clear and
   useful; UI is visually consistent with the rest of the app.

## Response

Created a functional specification for the Day 5.1 Search & Filtering feature
at `specs/008-search-filtering/spec.md`.

### Key Decisions

1. **Page-scoped search, not a single global bar across pages**: Each page
   (WorkoutList, Nutrition, ExerciseHistory) gets its own search input scoped
   to that page's data. This matches the existing architecture (pages render
   independently in DashboardLayout) and the constitution's S-principles.
   The constitution's "global search" concept was interpreted as "one
   consistent search experience across the app", delivered per-page.

2. **4 user stories (P1-P4), 18 acceptance scenarios**:
   - P1: Workout Search & Filter (name, notes, exercise names + category +
     date range) — the highest-value slice.
   - P2: Nutrition Search & Filter (food name + meal type + date).
   - P3: Exercise Search (exercise name).
   - P4: Clear Filters & URL state persistence (cross-cutting).

3. **21 functional requirements (FR-001 → FR-021)** covering search matching,
   category/date/meal-type filters, AND composition, debounce (200-300ms),
   empty states, clear-all action, state persistence, accessibility
   (labels, keyboard nav, aria-live), responsive layout, and dark-theme
   consistency.

4. **Zero [NEEDS CLARIFICATION] markers** — the constitution already defined
   S1-S10 principles and the user description specified all filter types,
   clear-all behavior, and UI rules. Reasonable defaults were documented in
   the Assumptions section (in-memory data, 250ms debounce, client-side
   string matching, no server search API).

5. **Key entities**: Workout (title, notes, exercises[].name, category, date),
   NutritionEntry (foodName, mealType, date), Exercise (name) — all mapped to
   existing codebase data shapes verified during exploration.
