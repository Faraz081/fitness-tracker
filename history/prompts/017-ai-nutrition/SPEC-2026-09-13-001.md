## Prompt

/sp.specify

Create a detailed functional specification for upgrading the existing Nutrition page into an AI-powered, real-time nutrition system based on the constitution already defined.

### Feature: AI-Powered Nutrition Page

#### 1. Overview
Upgrade the current Nutrition page so users can log food using natural language, receive structured nutrition estimates from Gemini, review/edit those values, save them to MongoDB, and immediately see meal sections, daily totals, and Dashboard nutrition data update from the same real records.

IMPORTANT:
- This is the project's existing Nutrition page.
- Keep the current UI, layout, black/orange theme, and design.
- Do not redesign the page or copy any external reference website structure.

#### 2. Existing Page Elements to Preserve
- Nutrition heading
- Add Entry button
- Filter Foods / Search Foods
- Breakfast / Lunch / Dinner / Snack filters
- Date selector
- Calories / Protein / Carbs / Fat summary cards
- Nutrition entries section
- Existing CRUD support for entries

#### 3. AI Food Search & Analysis
- Allow the user to type natural-language food descriptions such as:
  - "2 eggs"
  - "1 banana"
  - "1 bowl chicken biryani"
  - "200g grilled chicken with rice"
- Provide an "Analyze with AI" action.
- Send the food text to the backend.
- Backend calls Gemini using a server-side API key only.
- Gemini must return structured JSON only:
  - foodName
  - quantity
  - unit
  - calories
  - protein
  - carbs
  - fat
- Backend must validate the structured response.
- Quantity-aware estimates are required when quantity is provided.
- If quantity is missing, Gemini may estimate a reasonable serving.

#### 4. Editable AI Preview
- Show the AI result before saving.
- Allow the user to edit:
  - Food name
  - Quantity
  - Unit
  - Calories
  - Protein
  - Carbs
  - Fat
  - Meal type
  - Date
- Display a note such as:
  "AI-generated nutrition values — please verify before saving."
- Do not save anything until the user explicitly confirms/saves.

#### 5. Meal Selection & Saving
- User selects meal type: Breakfast, Lunch, Dinner, or Snack.
- After reviewing AI values, user saves the entry to the selected meal.
- Saved entry must include:
  - authenticated user ID
  - food name
  - meal type
  - quantity
  - unit
  - calories
  - protein
  - carbs
  - fat
  - date
  - timestamps if already supported
- Entry must appear immediately in the selected meal section.

#### 6. Date Behavior
- Default to today's date.
- Allow selecting another date.
- Entries must be stored with the selected date.
- Changing date must:
  - show only that day's entries
  - recalculate calories
  - recalculate protein
  - recalculate carbs
  - recalculate fat
  - recalculate meal totals

#### 7. Meal Filters
- Breakfast / Lunch / Dinner / Snack filters must use real database data.
- Selecting a meal filter shows only entries of that meal type for the selected date.
- No static/demo entries are allowed.

#### 8. Nutrition Summary
- Calories, Protein, Carbs, and Fat summary cards must be fully dynamic.
- Calculate totals from actual saved entries for the selected date.
- Totals must recalculate automatically after:
  - add
  - edit
  - delete
  - date change

#### 9. Entry Management
- Support view / edit / delete for saved entries.
- Edit must update the database and recalculate all affected totals.
- Delete must remove the record and recalculate all affected totals.

#### 10. Real-Time UI Updates
- After any mutation, the page must update immediately without manual browser refresh.
- Use the existing React state/query/API patterns to refetch or invalidate data after mutations.

#### 11. Dashboard Synchronization
- Dashboard nutrition values must come from the same Nutrition records.
- After add/edit/delete on the Nutrition page, Dashboard must reflect updated:
  - calories consumed
  - protein
  - carbs
  - fat
  - related nutrition progress/activity
- Do not maintain a separate dashboard-only nutrition dataset.

#### 12. Gemini Backend Security
- Store Gemini API key only in backend environment variables.
- Never expose the key in frontend code, VITE env vars, API responses, localStorage, or GitHub.
- Create a clean backend service/controller for AI food analysis.
- Handle missing key, API failure, and unidentifiable food gracefully.

#### 13. Error & Loading States
- Loading nutrition data: "Loading nutrition data..."
- AI processing: "Analyzing food..."
- No entries: "No nutrition entries for this date."
- Unidentifiable food: "Food could not be identified. Please try another search."
- API failure: clear retryable error message
- Prevent duplicate AI requests while analysis is in progress
- Do not generate fake nutrition values

#### 14. Acceptance Criteria
- [ ] Existing Nutrition UI and theme are preserved
- [ ] Natural-language food search works through Gemini
- [ ] AI returns structured nutrition JSON validated by backend
- [ ] AI values are editable before save
- [ ] Entries save with meal type, date, and user ID
- [ ] Meal filters and daily totals use real database data
- [ ] Add/edit/delete immediately updates meal lists and totals
- [ ] Date change filters entries and recalculates totals
- [ ] Dashboard nutrition values stay synchronized from the same records
- [ ] Gemini key remains backend-only
- [ ] Loading, error, and empty states are handled properly
- [ ] No static/mock nutrition data remains
- [ ] Users cannot access each other's nutrition records
